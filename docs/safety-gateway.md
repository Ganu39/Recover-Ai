# RecoverAI — Deterministic Policy & Safety Gateway (Phase 6)

This document provides the technical specification, trust boundaries, 12-stage safety check pipeline, decision precedence, idempotency semantics, rate limiting, kill switch, audit trail, and benchmark results for the **Deterministic Policy & Safety Gateway** (`gateway_version = "v1"`, `policy_version = "v1"`, `decision_version = "v1"`).

---

## 1. Objective & Architectural Boundary

The Deterministic Policy & Safety Gateway serves as the strict, non-execution gatekeeper between Phase 5 recommendation proposals (`RecoveryDecisionProposal`) and a future Phase 7 execution layer.

```text
Phase 4: AI Root-Cause Diagnosis (Advisory)
                  │
                  ▼
Phase 5: Recovery Decision Recommendation (Proposal Synthesis)
                  │
                  ▼
┌──────────────────────────────────────────────────────────────┐
│   PHASE 6: Deterministic Policy & Safety Gateway             │
│                                                              │
│  Stage 1:  Fail-Safe Kill Switch Check                       │
│  Stage 2:  Schema & Version Contract Validation              │
│  Stage 3:  Independent Proposal Identity Check (UUID5)       │
│  Stage 4:  Financial Integrity & Integer Minor Units         │
│  Stage 5:  In-Memory Idempotency & Replay Protection         │
│  Stage 6:  Executable Action Allowlist Check                 │
│  Stage 7:  Retry & Chronic Invariants Defense-in-Depth       │
│  Stage 8:  Failure Category & Hard Decline Safety            │
│  Stage 9:  High-Value Escalation & Human Approval Token      │
│  Stage 10: Sliding-Window Safety Rate Limiting               │
│  Stage 11: Final Gate Decision Synthesis                     │
│  Stage 12: Immutable Audit Record Logging                    │
└──────────────────────────────┬───────────────────────────────┘
                               │
            ┌──────────────────┴──────────────────┐
            ▼                                     ▼
        APPROVED                               BLOCKED /
(eligible_for_execution_layer = True)       REQUIRES_REVIEW /
            │                              RATE_LIMITED /
            ▼                              KILL_SWITCH_ACTIVE /
     Future Phase 7                        INVALID_PROPOSAL
    (Execution Layer)                             │
                                                  ▼
                                         Immutable Audit Trail
```

### Strict Non-Execution Invariants
* **Zero Razorpay Imports:** No Razorpay SDK, client, or webhook handlers are imported or referenced. Verified by automated AST scans.
* **Zero Payment Execution:** The gateway evaluates safety eligibility only; it never calls payment APIs, initiates retries, modifies subscriptions, charges customers, issues refunds, or sends notifications.
* **Zero Database Writes:** Evaluation runs strictly in-memory with in-memory idempotency and audit logs. Zero production table writes.
* **Meaning of Authorization:** `eligible_for_execution_layer = True` indicates solely that the proposal passed all deterministic safety controls and may be handed to a future Phase 7 execution boundary. It never triggers execution.

## 2. Trust Model & Input / Output Contracts

### Trust Model
1. **Trusted Observable Context (`GatewayTargetContext`):** Source of truth for financial amounts, attempt counts, customer history, and decline codes.
2. **Untrusted/Semi-Trusted Proposal (`RecoveryDecisionProposal`):** Generated by Phase 5; must be independently validated for identity, amounts, and invariants.
3. **Deterministic Gateway Policy (`GatewayPolicy`):** Frozen v1 rules and thresholds.
4. **Explicit Human Approval (`HumanApprovalRecord`):** Cryptographically/structurally valid authorization token from human operations supervisors.
5. **Air-Gapped Ground Truth:** `RecoveryGroundTruth` evaluation labels and raw LLM tokens are strictly forbidden from entering the gateway.

### Output Contract (`GatewayDecisionResult`)
* `gateway_decision`: controlled enum (`APPROVED`, `BLOCKED`, `REQUIRES_REVIEW`, `KILL_SWITCH_ACTIVE`, `RATE_LIMITED`, `INVALID_PROPOSAL`).
* `proposal_id`: UUID.
* `target_type`: `"payment"` | `"subscription"`.
* `target_id`: UUID.
* `decision_reason`: Human-readable explanation.
* `reason_code`: Machine-readable code (e.g. `APPROVED_FOR_EXECUTION_LAYER`, `BLOCK_RETRY_LIMIT_EXCEEDED`).
* `policy_version`, `gateway_version`, `decision_version`: Fixed to `"v1"`.
* `checks_evaluated`, `checks_passed`, `blocking_conditions`: Full traceability list.
* `audit_reference`: UUID.
* `eligible_for_execution_layer`: Boolean.
* `is_replay`: Boolean flag marking idempotent cached responses.

## 3. The 12-Stage Safety Check Pipeline

Every proposal is evaluated through twelve sequential deterministic stages:

1. **Stage 1 (Kill Switch):** Checks system-wide or scoped kill switch. If engaged or corrupted, immediately terminates with `KILL_SWITCH_ACTIVE`.
2. **Stage 2 (Schema & Version Validation):** Verifies that `decision_version == "v1"`, `policy_version == "v1"`, and `gateway_version == "v1"`. Prevents version downgrades or schema tampering.
3. **Stage 3 (Proposal Identity Recomputation):** Independently derives the deterministic UUID5 proposal ID using:
   $$\text{proposal\_id} = \text{uuid5}(\text{NAMESPACE\_DNS}, \text{"recoverai-decision-v1-v1-\{target\_type\}-\{target\_id\}"})$$
   Fails closed with `BLOCK_PROPOSAL_IDENTITY_MISMATCH` if any mismatch or tampering is detected.
4. **Stage 4 (Financial Integrity):** Strictly compares integer minor units (`proposal.amount_minor == target.amount_minor` and `proposal.currency == target.currency`). Floats and non-positive numbers are strictly prohibited. Mismatch triggers `BLOCK_AMOUNT_MISMATCH` or `BLOCK_CURRENCY_MISMATCH`.
5. **Stage 5 (Idempotency & Replay Protection):**
   - Exact duplicate proposal returns cached result with `is_replay = True` and avoids consuming a rate-limit slot (`IDEMPOTENT_REPLAY_APPROVED` / `IDEMPOTENT_REPLAY_BLOCKED`).
   - Conflicting proposal for the same target with different actions or amounts triggers `BLOCK_CONFLICTING_PROPOSAL_FOR_TARGET`.
6. **Stage 6 (Executable Action Allowlist):**
   - **Allowed Actions:** `RETRY_PAYMENT`, `RETRY_LATER`, `REQUEST_PAYMENT_METHOD_UPDATE`, `SUBSCRIPTION_RECOVERY_WORKFLOW`.
   - **Non-Executable Actions:** `NO_ACTION` $\rightarrow$ `BLOCKED`; `HUMAN_REVIEW` $\rightarrow$ `REQUIRES_REVIEW`.
7. **Stage 7 (Retry & Chronic Invariants Defense-in-Depth):**
   - Attempt Cap: `target_attempt_count >= 3` $\rightarrow$ strictly `BLOCKED` (`BLOCK_RETRY_LIMIT_EXCEEDED`).
   - Chronic Failure: History $\ge 3$ payments, success rate $< 25\%$, and unmitigated decline code $\rightarrow$ strictly `BLOCKED` (`BLOCK_CHRONIC_FAILURE_INVARIANT`).
8. **Stage 8 (Failure Category Safety):** Unrecoverable fraud codes (`suspected_fraud`, `stolen_card`) or generic declines without reliable history are blocked from automated retry (`BLOCK_UNRESOLVED_HARD_DECLINE`).
9. **Stage 9 (High-Value Safety & Human Approval):**
   - If `amount_minor >= 500000` (₹5,000) or proposal requires human review:
     - Missing approval token $\rightarrow$ `REQUIRES_REVIEW` (`HIGH_VALUE_REQUIRES_REVIEW`).
     - Invalid/mismatched/empty approval token $\rightarrow$ `REQUIRES_REVIEW` (`INVALID_HUMAN_APPROVAL`).
     - Valid human approval $\rightarrow$ passed to Stage 10.
     - *Important Invariant:* Human approval cannot override hard attempt caps or chronic failure invariants.
10. **Stage 10 (Safety Rate Limiting):** Evaluates sliding-window attempt counters per target (max 3 per hour) and customer. Exceeded counters trigger `RATE_LIMITED`.
11. **Stage 11 (Final Gate Synthesis):** Marks `eligible_for_execution_layer = True` and `APPROVED_FOR_EXECUTION_LAYER`.
12. **Stage 12 (Audit Logging):** Records immutable `GatewayAuditRecord` in append-only in-memory log.

## 4. Idempotency & Conflict Semantics

### Primary Replay Rule
* Key: `(proposal_id, gateway_version, policy_version)`.
* Replaying an already-approved proposal returns the cached approval with `is_replay=True` and does not consume another rate-limit slot.
* Replaying an already-blocked proposal maintains the deterministic blocked outcome with `is_replay=True`.

### Target Conflict Rule
* A proposal conflicts with stored state if:
  1. An execution-eligible (`APPROVED`) proposal already exists for `(target_type, target_id)` with a different proposal ID and either a different `action_type` or a different `amount_minor`.
  2. A second conflicting action is proposed for the same unresolved target within the active session.
  Result: `BLOCKED` with `BLOCK_CONFLICTING_PROPOSAL_FOR_TARGET`.

---

## 5. Rate Limiting & Kill Switch

### In-Memory Sliding-Window Rate Limiter
* Target Window: Maximum 3 authorization attempts per target per 3,600-second window.
* Customer Window: Maximum 9 authorization attempts across targets for the same customer per window.
* Idempotent replays are detected prior to rate-limit recording and do not consume quota.

### Fail-Closed Kill Switch
* When active, all incoming non-replayed requests return `KILL_SWITCH_ACTIVE` (`eligible_for_execution_layer = False`).
* If configuration is missing, corrupted, or unreadable, the kill switch automatically engages (`fail-closed`).
